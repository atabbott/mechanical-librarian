# Roadmap

Milestones are outcome-based. Dates should not be promised until the preceding
milestone has met its exit criteria.

During pre-release development, the numbered delivery groupings are internal
checkpoints rather than release-publication commitments. The roadmap milestones
and numbered checkpoints retain all of their exit criteria whether or not a
release is published. Completing one does not create a tag, GitHub Release,
supported version, or published release artifact. The first release publication
requires a separate maintainer decision selecting a checkpoint with genuinely
usable functionality that provides value to the owner or another user, followed
by every applicable release gate and release-publication gate. This roadmap
selects neither that checkpoint nor its version. After the first published
release, maintainers may explicitly designate later milestones as release
trains; release publication does not make that automatic.

### Completed 0.16.0 engineering health

Every check the contributor documentation promises is enforced by the public
gate, the worst structural debt is paid down, and a clean checkout passes every
documented source check on the first run. The milestone ends with the same
product behaviour under a stricter, truthful quality floor, and with measurably
less code: duplication and longhand ceremony are removed wherever a refactor
already touches them, never at the cost of an invariant, an assertion, or a
bound.

### Completed 0.16.1 documentation economy

The corpus and the runtime contract shrink to what is load-bearing. Superseded
historical documents are deleted, git history being the archive and ADRs
untouched; duplicated contracts collapse to single authorities, code-shadowing
prose becomes pointers, and CI enforces reachability and link integrity
(#683-#686, #717). The capped engineering follow-ups are an evidence-based
test-value audit with pruning, and container runtime hardening. Deletion pull
requests name what they removed and the last SHA containing it.

### Completed 0.16.2 write-path truth and signal integrity

A guarded write that is refused reports the thing that refused it: a storage
fault is no longer relabelled an unacceptable decision, a withdrawn consent or
a revoked authority, startup recovery attempts every pending plan instead of
stopping at the first, a permanent refusal answers 409 rather than inviting a
retry, and a failed provider-recovery database or cover stage names the disk
failure it hit (#677-#679, #715, #734). Qualification signals were repaired so
a failure means what it says: a package-mirror stall no longer consumes the
protected browser budget, the scale qualifier no longer fails for its own
reasons, every direct dependency must carry an authority grant, a Library row
is read at its declared width rather than padded by a narrow double, reserved
test ports are held to the bind, and `bootstrap.composition`'s unreached
mutants were judged rather than scored — 287 now tested, the rest accepted in
writing beside what proves them, the largest of those accepted as unproved
(#711, #755, #769, #770, #772-#774). The type gate now enforces `arg-type`
across the test tree, so a double bound into a port it does not satisfy fails
the gate; the 48 modules carrying findings are named as the burn-down backlog
(#693).
